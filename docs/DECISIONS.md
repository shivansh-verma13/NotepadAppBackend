# Decisions

## Workspace mutation ordering — October 18, 2026

Proposal: admit only one create/edit/delete request at a time in the mounted workspace, using a synchronous ref guard plus disabled controls and an announced pending operation. Keep the existing whole-library API response contract and reject results from an invalidated session.

Challenge: applying per-note response patches permits parallel writes but needs reliable create identity/version contracts and careful reconciliation of stale snapshots. Server revisions/conditional writes coordinate tabs/devices but add an API and persistence contract. The current API returns entire arrays and the bounded workspace has no revision field; response arrival order cannot establish write order.

Decision: use the shared workspace guard for this bounded data-loss fix; do not queue surprise mutations. Release it on success/failure, retain failed drafts and permit search while waiting. Deferred synthetic tests cover blocked overlap, delete retry, edit retry and old-session responses arriving during a newer mutation. This is single-workspace response ordering only, not cross-tab concurrency control, idempotency or cancellation of a write after an HTTP timeout. Revisit server revisions/idempotent create before claiming safe ambiguous-timeout retry or multi-client editing; reverse this UI revision if supported checks or real browser keyboard/CRUD flows regress. Backend contract, persistence and deployment order stay unchanged.


## Vite implementation coordination — October 14, 2026

Proposal: complete the previously selected frontend Vite migration without changing Express/Mongo, API response keys, cookie/Origin/header authentication or persistence.

Challenge: standalone Jest keeps all 18 existing frontend behavior tests with explicit Babel/lint configuration; Vitest would unify transforms but adds test-framework migration. Both are viable; frontend docs/DECISIONS.md records versions, evidence and limits. Forced incompatible dependency upgrades would obscure support instead of resolving the gate.

Decision: retain Jest in this bounded slice. Frontend keeps public REACT_APP_API_URL, port 3000 and build/ output (generated modules move to assets/); automatic VITE_* exposure is disabled. Document modern browser targets and Netlify SPA fallback with same-origin API proxy precedence. Node 22.12+/24 is required for the paired local setup. Revert the frontend revision on CI/browser/host regressions; revisit the test framework if remaining tool-only advisories cannot be safely repaired. No backend runtime, hosting, data or deployment change. Existing paired auth rollout and owner-approved username index gates remain.

Proposal: retain the existing Express/Mongo API while the frontend finishes compatible dependency patches and then replaces CRA with Vite in a separate bounded slice.

Challenge: retaining patched CRA minimizes change but leaves incompatible pinned toolchain chains; a custom webpack/Jest setup preserves conventions while adding maintenance responsibility. Vite changes frontend entrypoints/environment/testing and requires explicit parity checks, but does not require backend architecture, credentials, persistence or deployment changes. See the paired frontend docs/DECISIONS.md for audit evidence and official React/Vite sources.

Decision: select Vite for the next frontend build-tool slice, retaining React/UI/business logic and the /notepad API, cookie/Origin/header boundary and public API URL configuration contract. Require install/lint/behavior tests/build, asset/SPA fallback and available browser checks. No backend runtime change or deployment in this patch slice; existing paired rollout/index approval gates remain. Reconsider if a bounded spike cannot preserve those contracts without broad changes. Reverse frontend patches on CI/build regression; no data or infrastructure rollback is needed.

## Notes slice 1: refactor the save boundary
Proposal: retain React 18/MUI and Express/Mongoose, keep endpoint and response contracts, replace whole-user read/mutate/save with owner-scoped atomic Mongo operators and preserve failed UI drafts.
Challenge: a Vite/TypeScript rebuild would simplify the aging CRA toolchain, but it delays fixing data loss and mixes API migration with UI replacement. A separate notes collection supports pagination better but requires an explicit data migration.
Decision: focused refactor now. Verify save/failure semantics first; revisit Vite after the authenticated journey works. Reverse this choice when CRA blocks build/test or the redesigned UI needs clean entrypoints. Introduce a dedicated notes collection only after measured query needs and a recoverable migration plan.

## Scheduling
Proposal: use the available desktop scheduled task, invoking the installed ChatGPT-authenticated Codex CLI in isolated checkouts.
Challenge: GitHub Actions plus the official Codex integration is always-on but requires API credentials/credits absent in this account; Windows has no cron daemon. A custom Windows Task Scheduler service would add installation/access beyond the existing scheduler.
Decision: supported desktop automation plus a reusable bounded CLI wrapper. Verified GitHub identity and CLI login; no new token or billing. Desktop app/computer availability is a limitation, and runs can be delayed. Switch to a cloud runner when an API budget and repository-scoped credentials are supplied. Manual wrapper works independently of this chat. The app scheduler is the only recurring trigger; no push trigger can recursively launch it.

Access: existing authenticated gh/git session, no additional repository access granted. The application allowlist restricts eligible changes; the existing session itself may have broader account permissions. For credential-level isolation use a fine-grained GitHub token limited to the active two repos with Contents and Pull requests read/write plus Metadata read, stored in the OS credential manager, never in these files. Do not silently claim the existing account login is a repository-scoped token.

## Notes slice 2: authenticated local integration
Proposal: keep signed host-only JWT cookies; configure exact frontend origins, require an allowed Origin plus X-Notes-Request: 1 for every mutation (including login/register/logout), use POST logout, and default to SameSite=Lax. Configure Secure production cookies; cross-site SameSite=None is an explicit HTTPS-only option. Test with a temporary real local MongoDB and synthetic accounts.
Challenge: a synchronizer CSRF token also protects cookie sessions but needs a token lifecycle/bootstrap endpoint. Bearer tokens avoid cookie CSRF but require a new storage/refresh model and increase exposure to script access. Exact-origin plus a non-simple header fits the existing browser-only API, rejects forms and requires CORS preflight; it depends on an exact trusted-origin allowlist.
Decision: cookie plus Origin/header gate for this bounded release, with host-only scope and shared issue/clear options. No wildcard origins or GET mutations. Validate configuration before startup and stop on database failure. Revisit synchronizer tokens if non-browser clients or proxy deployments cannot preserve Origin, or if trusted-origin boundaries change. Do not loosen origin checks to accommodate a deployment. Backend contract must ship with the paired frontend before any preview; production remains unchanged.

## Notes slice 3: bounded account attempts
Proposal: protect the existing account endpoints with a shared per-socket-IP fixed-window budget before parsing/validation/bcrypt, a bounded per-process store, and an explicit retry response.
Challenge: a Redis/edge-backed limiter offers distributed budgets and survives restarts, but adds unapproved infrastructure/configuration. An account-key limiter stops distributed guessing but permits deliberate username lockout. Existing code has no proxy trust configuration or shared limiter service; a process-local guard is viable for local verification but cannot establish a hosted security boundary.
Decision: 20 combined login/register attempts per 15 minutes, at most 10,000 address keys, fail closed at capacity; ignore forwarded headers. Preserve session/logout/notes routes and all existing contracts. Show retry guidance without discarding fields. Do not claim distributed protection; require proxy-chain/shared-budget verification before preview. Reverse to a shared edge/store-backed budget before multi-worker hosting or when legitimate NAT traffic shows this budget is too restrictive. Keep username index operations manual and blocked on a duplicate audit, approved backup and recovery plan.

## Notes slice 4: explicit username uniqueness rehearsal — October 11, 2026
Proposal: declare a named exact-case unique username index as schema metadata, retain connection autoIndex=false, and map only username duplicate-key failures to the existing redacted 409 contract. Build the index explicitly only in disposable synthetic integration tests.
Challenge: an application-only check or keyed mutex avoids an index rollout but cannot enforce uniqueness across processes/restarts. A dedicated account-identity collection with a unique key can enforce ownership but requires a recoverable account migration. The existing embedded-user model supports a named unique index with no data-model migration; legacy duplicates can prevent its build.
Decision: retain the model and exact case semantics; rehearse rejected builds preserving duplicate fixtures, a successful explicit index, and deterministic simultaneous registrations. No startup index build or live data cleanup. Deploy API collision handling before any owner-approved index build; pause registration during final audit/build. Revisit the identity collection if approved recovery reveals incompatible legacy records or identity semantics change. A failed index build leaves registration paused and records intact; API rollback retains a successful unique index.

## Workspace search and test dependency boundary — October 17, 2026
Proposal: filter the authenticated, already-loaded notes by literal case-insensitive title/content substring, with a bounded 200-character query kept only in component state. Distinguish initial loading, failed read/retry, empty library and no search matches; preserve the filter across successful mutations.
Challenge: a server search endpoint supports larger libraries and pagination, but adds API/query contracts to an embedded-note model whose create cap is 200 (legacy larger libraries remain readable). Local filtering preserves source-scoped existing reads and avoids transmitting or persisting search text. It does not claim pagination or large-library performance. Do not show capture before the initial read completes, preventing a late initial response from replacing a newly saved note.
Decision: use local search for this bounded criterion-4 slice, retain stable IDs for filtered edits/deletes, and verify real components against synthetic mocked API responses. Revisit server pagination/search when measured legacy-library size or a dedicated-note model requires it; reverse this UI revision if supported checks or browser flow regress. No API/persistence/hosting change.

Tooling evidence: fresh npm audit still reports 19 moderate tool-only findings rooted in @istanbuljs/load-nyc-config -> js-yaml 3 -> argparse 1 -> sprintf-js. Registry latest Jest/babel-jest 30.5.2, babel-plugin-istanbul 8.0.0 and loader 1.1.0 retain this chain; latest YAML 3.15.2 still requires argparse 1. Official advisory https://github.com/advisories/GHSA-hp3w-g68c-fv3c lists no patched sprintf-js version. Keeping Jest 30 with explicit debt preserves the 25 baseline cases; migrating to Vitest 5 is viable but requires a separate test-global/mock/environment migration and parity check. Reject npm's suggested Jest 25 downgrade and forced YAML/argparse overrides. Keep the lockfile unchanged, retain this release blocker and time-box a separate Vitest parity spike rather than repeatedly attempting compatible patches that do not exist. No clean-audit claim.

## Safe create retry — October 20, 2026

Proposal: accept an optional timestamped random create key and atomically append a bounded owner-scoped receipt with the embedded note. Keep the same key and exact draft for uncertain retries; return the current library without another insert. Retain receipt hashes after edit/delete to prevent recreation.

Challenge: a separate uniquely indexed receipt collection plus transaction supports independent retention but needs transaction-capable hosting, new indexes and rollout coordination. Embedded receipts use the existing single-document atomic boundary without migration; they add bounded per-account storage and a write ceiling. A process-memory cache cannot survive restarts or coordinate workers. Existing notes are embedded, capped at 200 new notes, and writes already use findOneAndUpdate.

Decision: optional body createKey = epoch-milliseconds.UUID, accepted for 24 hours with at most 60 seconds of future clock skew. Reject expired keys even after pruning; store SHA-256 of the normalized title/content, never extra draft copies. Atomically require absent key, fewer than 1000 unexpired receipts and the existing note cap; fail closed at receipt capacity. Prune only expired receipts; matching replay returns 201/current notes, different payload returns 409. Legacy requests without keys retain their contract but lack retry protection. Frontend holds the key/draft in mounted capture state and locks editing after uncertain transport/server failure until resolved; no automatic retry or browser storage. Deploy compatible backend first, frontend second. Revisit a transactional dedicated collection if measured traffic/storage needs exceed this bound; reverse paired code on regression while preserving receipts through the retry window. No live data/index/hosting action. Synthetic concurrency, commit-then-response-loss, owner isolation, deletion, cap, expiry and UI tests required; browser verification remains separate.


## Conditional note revisions — October 21, 2026

Proposal: retain embedded notes and add a nonnegative integer revision. Conditional edits/deletes match owner, note ID and expectedRevision in the same atomic operation; edits increment the revision, including legacy unconditional writes. Missing legacy revisions compare as zero without a data migration. Stale existing notes return a redacted 409 NOTE_CONFLICT; missing/foreign notes return the same 404.

Challenge: a separate notes collection with per-document versioning supports pagination but requires a migration and coordinated rollout. A whole-library version is also viable without migration, but unrelated note changes would conflict. Per-note embedded compare-and-swap fits the existing atomic boundary and avoids false conflicts between different notes. Optional revision requests preserve old-client compatibility; old clients remain unconditional and cannot be promised stale-write protection.

Decision: optional expectedRevision in PATCH/DELETE JSON bodies; safe integers below Number.MAX_SAFE_INTEGER only. New notes start at zero; reads expose zero for legacy notes through the schema default. UI always submits its loaded revision, retains conflicted edit text as selectable read-only content and disables repeat submission until the user copies it and reloads. Never automatically rebase/retry a stale write or replace the library on conflict. Reopening a closed editor starts from the currently displayed note. Deploy API first, UI second; reverse UI first on regression while retaining revision fields. Revisit dedicated storage when measured pagination/size needs justify migration. Require real synthetic Mongo concurrency/reconnect/owner isolation, UI draft retention and HTTP serialization tests. Browser/hosted verification remains a separate gate.

## Explicit conflict comparison — October 22, 2026

Proposal: fetch the authenticated owner's existing all-notes endpoint only after an explicit conflict-recovery action, extract the selected note and show its title/content/revision beside the retained draft. Keep comparison reads separate from the workspace snapshot. Require an explicit choice to continue editing the draft against the fetched revision, followed by a separate save.
Challenge: a new owner-scoped single-note endpoint reduces payload but adds paired API surface without changing the existing all-notes read contract (legacy libraries may exceed the create cap). Reloading the library is viable but can unmount filtered/deleted notes and lose the unsaved draft. Automatic retry/rebase could overwrite changes the owner has not reviewed. Existing authenticated reads already enforce owner scope; no new persistence or infrastructure is needed.
Decision: reuse the existing read contract with session checks and cancellation on close/unmount; reject malformed selected-note data, show read failures/deletion honestly, retain the draft and prevent duplicate reads. Do not replace workspace state or automatically advance revisions. A missing note cannot be recreated by this flow. The fetched version is a snapshot, and conditional writes still detect later changes. Reverse the frontend slice on regression; API-first deployment order from the existing accumulated PR remains required. Revisit a single-note endpoint with measured library/pagination needs. Require synthetic failure/missing/session/race/repeated-conflict tests and desktop/mobile browser verification before merge.
